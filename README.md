# BeautyScale — Brand Order Requests

A multi-tenant app for the brand order request workflow. A beauty brand
publishes its catalogue, a buyer submits an order request, and the brand's
sales team accepts it — which creates a draft order and reserves stock
atomically — or rejects it.

Several brands share the app. Each brand is a workspace, and no workspace can
read or mutate another's data.

## Run it

### With Docker

```bash
cp .env.example .env

make backend-up          # PostgreSQL and the API
make seed                # demo data; prints the workspace IDs
```

The seed prints a line per workspace. Paste the IDs into `VITE_WORKSPACES` in
`.env` as a JSON array, then build the client:

```bash
docker compose up -d --build web     # http://localhost:5173
```

The seed comes before the client build because Vite inlines `VITE_*` values at
build time, and the workspace IDs are generated by PostgreSQL — so they cannot
be known earlier. `make up` builds everything in one go, which is fine once
`.env` already holds the IDs.

```bash
make down                # stop, keeping the data
make down-volumes        # stop and discard the database
```

`make help` lists every target. Each app also has its own Makefile and its own
`docker-compose.yml`, so either side runs alone: `make -C backend help`.

### Without Docker

Needs Go 1.26, PostgreSQL 17, the [Atlas CLI](https://atlasgo.io) and Node 22.

```bash
# backend
cd backend
cp .env.example .env     # set DATABASE_URL
createdb bscale_dev
make migrate-apply       # create the schema
make seed                # demo data; prints the workspace IDs
make api                 # http://localhost:8081
```

```bash
# frontend, in another terminal
cd frontend
cp .env.example .env     # set VITE_WORKSPACES from the seed output
npm install
npm run dev              # http://localhost:5173
```

## Using it

Open http://localhost:5173, or the deployed client at
https://beauty-scale.netlify.app.

1. **Buyer** — pick a workspace in the header, browse or search the catalogue,
   set quantities, add them to the request, enter a name and email, submit.
   The confirmation shows the request and its total.
2. **Sales** — the new request is listed. Filter by status, open it to see the
   lines and the total, then Accept or Reject. Accepting decrements stock and
   creates a draft order; rejecting leaves stock untouched.

The workspace switcher is a demo convenience, not authentication: it only
decides which `X-Workspace-ID` header is sent. The API derives the tenant
solely from that header, which it validates.

## Tests

```bash
make test                # the whole backend suite
```

The integration tests read `TEST_DATABASE_URL`, falling back to
`DATABASE_URL`, and skip themselves when neither is set. Point them at a local
PostgreSQL rather than a remote one — see the note about the seed under
shortcuts.

The tests that cover the risky parts, all in
`backend/internal/modules/orderrequest/`:

| Test | What it proves |
| --- | --- |
| `TestAcceptReservesStockAndCreatesDraftOrder` | Accepting decrements stock and creates exactly one draft order |
| `TestAcceptTwiceIsRefused` | A second accept is a `409`, with no duplicate order and no second deduction |
| `TestConcurrentAcceptsProduceExactlyOneOrder` | Eight simultaneous accepts: one `200`, seven `409`, one order, stock moved once |
| `TestConcurrentAcceptsCannotOversell` | Concurrent accepts across requests never drive stock negative |
| `TestAcceptWithInsufficientStockChangesNothing` | A short line rolls the whole transaction back, leaving no partial change |
| `TestCrossWorkspaceAcceptIsRefused` | One workspace cannot accept another's request |
| `TestWorkspaceIsolation` | One workspace cannot read another's requests — `404`, not `403`, so absence leaks nothing |
| `TestCreateIgnoresClientSuppliedPrices` | Prices come from the database, never the request body |
| `TestCreateSnapshotsSurvivePriceChanges` | A later price change does not rewrite a submitted request |
| `TestEndpointsRequireAWorkspaceHeader` | Every scoped endpoint rejects a missing or malformed header with a clear `400` |

The concurrency tests run real parallel transactions through a `pgxpool`
against PostgreSQL, because an in-process fake would not exercise the row locks
that make the accept correct. Other integration tests run inside a transaction
that is rolled back, so the suite leaves no rows behind.

The frontend is covered by `npm run typecheck` and `npm run lint`; it has no
component tests — see the shortcuts below.

## Design choices

**Tenancy is enforced in the schema, not only in code.** Every tenant-owned
table carries `workspace_id NOT NULL`, and child rows use composite foreign
keys on `(workspace_id, id)` rather than plain `id`. A row referencing a parent
in a different workspace is rejected by PostgreSQL, so a forgotten `WHERE`
clause cannot silently cross tenants. A foreign ID returns `404`, not `403`,
because `403` would confirm the row exists.

**Accept is one transaction, ordered to make deadlock impossible.** It selects
the request `FOR UPDATE`, checks the status is `new`, aggregates quantities by
product (a product can appear on two lines), locks the product rows **in
product-ID order** so two concurrent accepts take the same locks in the same
sequence, verifies stock, decrements, writes one order and its items from the
price snapshots, then flips the status. A unique index on
`(workspace_id, order_request_id)` is the second line of defence: even if the
status check were ever wrong, the database would refuse a second order.

**Money is `NUMERIC(12,2)`, carried as decimal strings.** It never passes
through a float, in Go or in JSON. A request must use one currency, enforced in
the service layer, so a single total is meaningful.

**Prices are snapshotted.** Request and order items store the product name,
unit price and currency as they were at submission, so a later catalogue change
does not rewrite history or a total the buyer already agreed to.

**Email goes through a transactional outbox.** The accept transaction inserts
the notification row; a worker claims it with `FOR UPDATE SKIP LOCKED`, sends
it, and records the attempt with bounded retries and backoff. The HTTP response
returns after the commit, never after delivery, so a provider outage cannot
roll back an accepted order or slow the request. With no `BREVO_API_KEY` the
sender logs the message instead, which is what the assessment asks for.

**Pagination, search and filtering are entirely in SQL**, with parameterized
queries and `created_at DESC, id DESC` for stable ordering. Nothing fetches all
rows to paginate in the browser. TanStack Query keys include the workspace ID
and every page, filter and search parameter, and the cache is cleared when the
workspace changes.

**One generic `DataTable<T>`** takes columns, data and row actions from the
calling feature; the row renderers live in `frontend/src/components/rows/`.
Order requests expose View, Accept and Reject — not Edit or Delete, which are
not part of the workflow.

The backend README goes deeper on all of this, including the indexes and the
exact SQL behind the accept.

## Shortcuts I took

- **No authentication.** The workspace comes from the `X-Workspace-ID` header,
  as the brief allows. The switcher in the UI is a labelled demo control, and
  anyone can send any workspace ID. Real tenancy would derive the workspace
  from a verified session and never from a client header.
- **The frontend has no component or end-to-end tests.** I spent the testing
  budget on the backend, where the risk is — concurrency, money and tenant
  isolation. Typecheck and lint run clean, which catches shape errors but
  proves nothing about behaviour.
- **Migrations are not applied automatically on deploy.** I run
  `make migrate-apply` against the production database by hand. A pre-deploy
  hook running Atlas would remove that manual step.
- **The seed's workspace IDs are database-generated**, so the frontend needs a
  copy-paste step after seeding. Deterministic UUIDv5 from the slug would let
  both sides agree without it.
- **The seed looks products up one at a time.** Against a local database that
  is instant, but over a remote one the 344 round trips push the two
  idempotency tests past their 30-second deadline. Batching the lookup into a
  single `WHERE name = ANY($1)` would fix it; the seed is a developer tool, so
  it was not where I spent the time.
- **Mixed-currency requests are blocked rather than supported.** Grouping
  totals per currency is the better product answer, but one currency per
  request keeps a single total meaningful, and a check constraint for it would
  need a trigger.
- **Expiry writes `rejected` with a timestamp rather than a fourth status.**
  Adding `expired` to the status check constraint would have touched the
  constraint, the API's status filter and the UI badges; the backend README
  records the trade-off.
- **No observability.** There is structured logging via `log/slog` and a
  `/health` endpoint, but no metrics, tracing or error reporting.
- **CORS is wide open on the deployment** (`CORS_ALLOWED_ORIGINS=*`), so the
  Netlify client can reach the Railway API without a per-environment origin
  list. The API carries no credentials or cookies, so this exposes nothing a
  reader could not request directly — but it should be the client origin and
  nothing else.

## What I would do next

1. **Frontend tests** — Vitest and React Testing Library over the cart
   reducer, the request form's validation, and a Playwright run of the full
   buyer-submit-to-sales-accept path.
2. **Optimistic concurrency in the UI.** Two salespeople on one request still
   race to the same `409`; the loser sees a correct error but a stale row.
   Refetching the detail on `409` would show them why.
3. **Automatic migrations on deploy**, as a release command gated on
   `atlas migrate status`.
4. **Per-currency totals**, which would let a buyer mix catalogues.
5. **Rate limiting and request size caps** on the public endpoints.
6. **A real auth boundary** — sessions, roles, and the workspace derived from
   the session rather than a header.
7. **Metrics and tracing** — accept latency, outbox lag, stock-rejection rate.

## Deployment

Both halves are deployed, and the demo link is the place to start:

| | |
| --- | --- |
| Client | https://beauty-scale.netlify.app — Netlify, static build |
| API | https://beauty-scale-backend-production.up.railway.app — Railway, from `backend/Dockerfile` |
| Database | Neon, serverless PostgreSQL 18 in `ap-southeast-1` |

```bash
curl https://beauty-scale-backend-production.up.railway.app/health
```

Open the demo, pick a workspace in the header, submit a request on the Buyer
page, then accept it on the Sales page. Ten seeded brands are available in the
switcher, each with a catalogue of 30 to 50 products.

Two notes on how it is wired:

- **The API reads `PORT` when the platform injects one**, falling back to
  `HTTP_PORT` and then `8081`, so the same image runs locally and on Railway
  without an override.
- **`CORS_ALLOWED_ORIGINS` is `*` on the deployment**, which is what lets the
  Netlify origin call the Railway API. For anything beyond a demo it would be
  the client origin and nothing else.
- **The client is a static build**, so `VITE_API_BASE_URL` and
  `VITE_WORKSPACES` are inlined at build time and set in Netlify's own
  environment, not read at runtime.

## Repository layout

```
.
├── docker-compose.yml     PostgreSQL, the API and the client together
├── .env.example           shared placeholders for Compose
├── Makefile               whole-stack commands
├── backend/               Go API, migrations, seed, tests
└── frontend/              React client
```

No secrets are committed. `.env` is ignored repository-wide, and all three
`.env.example` files hold placeholders only. The seed data is invented — there
is no real customer data anywhere in the repository.
